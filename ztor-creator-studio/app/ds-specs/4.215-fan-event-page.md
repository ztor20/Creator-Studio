### 4.215 Fan page mirror（前台鏡像；原名 Fan event page） 

**Pattern** — 5.1.13 Pre-publish preview 的預覽那一半，見 [5-pattern.md](../ds-pillars/5-pattern.md)。

**Purpose** — 發布前預覽確認（主規格 §7.4）用於活動的預覽檢視，D305（2026-09-22）把它從一張活動卡改成「粉絲視角完整頁」：內容等同粉絲端活動頁會呈現的全部設定，活動有票券頁與票務商品頁兩個視圖（沒有組合包時只有票券頁）。**2026-09-22 使用者裁決：「預覽 UI 必須做得和這兩個一模一樣，只是資料和機制套用我們的流程與功能」**（票券頁 `https://ztor.vercel.app/shop-item.html?id=ev-score-live`、票務商品頁 `…?id=ev-themesong-night&sets=1#bundles`）。所以本元件自同日起不再是用站上 token 重刻的結構鏡像，而是**前台的真實 markup 與 CSS**：`js/fan-event-page.js` 輸出前台兩頁 `<main>` 的 DOM 結構與 class 名（證據 `docs/fe-mirror-2026-09-22/ticket.main.html`／`bundles.main.html`），`ds-components/fan-shop.css` 是那兩頁實際命中的全部 CSS 規則（Playwright 抽出，加 `.fep-shop` 前綴、`:root`／`html`／`body` 改 `.fep-shop`、@font-face 移除改用站上自架字型）。只有資料換成我們的：名稱、亮點、描述、卡司、須知、取票方式、票種、組合包（允許票種 × 張數、商品、權益、售價／原價）全部來自建立活動流程或 events-store。兩個宿主——`create-event.html` 發布前、`event-detail.html` 的「預覽與在地化」——共用同一支渲染函式。

**與前台的差別（刻意）** — 前台專有互動拿掉：`pdp-topbar` 保留 markup 但不可點、「情境展示」浮鈕與 `pdp-sheet` 抽屜不畫、購買類按鈕（購票／購買／購買組合／收藏／購物車）`data-pp-inert` 不動作；相關活動三張卡標「非本活動」（`relatedFromStore()` 從 events-store 撈別的活動，宿主呼叫）；亮點（D300）前台沒有位置，放名稱下方一行 `.pdp-buy__highlight`；退換票表單沒有此欄，前台那句當平台固定文案（`fep.refund.fixed`）；描述是一個可翻譯欄位，整段放前台的 lead 段（一個 contenteditable 拆不成 lead＋para）；金額補成前台的「NT$ 1,200」（符號後空格）。細節見 ASSUMPTIONS UIA-167。

#### 4.220 Fan project page（粉絲視角專案頁，前台共創／預購頁與標題頁鏡像）

**Purpose** — 建立專案最後一步「預覽與發布」（§4.216 Publish stage）用於專案的預覽檢視（D322，2026-09-23，比照 D310 建立活動全頁化、D317／D321 建立商品／組合改兩步驟）：Fan event page（§4.215）／Fan product page（§4.215（商品頁））／Fan bundle page（§4.215（組合包頁））的專案版，同一套「前台 1:1 鏡像」做法——內容等同粉絲端專案頁會呈現的全部設定，依 `model.kind` 分三種：直接發行（`golive`，前台 `title.html` 的 `.detail-hero`＋逐段 `.detail-section`）、共創（`fund`）與預購（`preorder`，兩者共用前台 `cocreate-project.html` 的 `.cocreate-detail`）。`js/fan-project-page.js` 讀前台原始碼（`cocreate-project.html`：`?kind=music&state=active`／`?kind=preorder&state=active`；`title.html`）輸出對應的 DOM 結構與 class 名；CSS 是 `ds-components/fan-shop.css` 第 6 段「專案頁元件」，延續第 1–5 段（Fan event page／Fan product page／Fan bundle page）已建好的 `.fep-shop` 前台 token，不新增裸值例外。只有資料換成我們的——名稱、海報、圖庫、關鍵字、描述或故事、方案（回饋套組／預購方案）、預算分配、交付時程全部來自建立專案表單；購買／支持類互動一律不動作；剛發布的專案一律畫成「計畫進行中、0 人支持、0%」；不畫相關推薦、留言討論、浮動支持條、製作進度時間軸（建立流程沒有這批資料）。**2026-09-23（D323）作品上架流程重用**：`publish-work.html` 的最後一步「預覽與送審」沿用本元件（只用直接發行影片版型，`model.kind:'golive'`），新增三個選填 model 欄位供這個消費頁使用——`model.work`（布林旗標，作品模式下沒有故事也沒有條列時不畫空的「關於這部作品」段）、`model.credits`（有值才畫「創作團隊」段）、`model.clips`（有值才畫「預告與花絮」段）；create-project.html 不傳這三欄，畫面與先前一致。

**Behavior** — 宿主（`create-project.html`／`publish-work.html`）把表單資料整理成一份 `model`（結構見 `js/fan-project-page.js` 檔頭：`kind`／`film`／`work`／`name`／`desc`／`story`／`creator`／`poster`／`media`／`hasTrailer`／`facts`／`langLabel`／`langValue`／`keywords`／`meta`／`access`／`price`／`fund`／`delivery`／`tiers`／`budget`／`credits`／`clips`）交給本檔渲染，本檔只知道「粉絲專案頁長什麼樣」、不知道資料來源；`work`／`credits`／`clips` 三個選填欄位僅 D323（publish-work.html）傳入，見上方 Purpose 與 Anatomy。可翻譯欄位（`name`／`desc`／`story`／逐方案 `name`／`benefits`／逐預算分類 `label`）由宿主給 `{ key }`，本檔以 `api.getValue(key)` 取當前語系值並掛 `api.bindEditable`。金額一律用前台「代碼＋空格＋千分位」寫法（`codeMoney()`），不補符號。共創／預購募資面板固定顯示 0 人支持、0%、進度條 `--bar-fill:0%`——剛建立的專案沒有真實募得數字。交付時程的預期交付日期是本檔唯一的表單控件（`<input type="date" data-fpj-delivery-input>`），宿主監聽其 `change` 寫回自己的單一來源（`#cpp-delivery` 或預購的 `#po-delivery`）並呼叫 `stage.refresh()`；未填時顯示提醒句「必填 · 粉絲在支持前會看到這個日期」。預算分類配色依序輪替站上既有圖表色（不沿用前台固定三色，分類數量與名稱由創作者自填、不固定）。價格只看不改（D514）。本檔不畫相關推薦、留言討論、浮動支持條與製作進度時間軸（建立流程階段沒有對應資料，不生造佔位內容）；創作團隊改為選填（`m.credits` 有值才畫，見上方 Anatomy），create-project.html 不傳、publish-work.html（D323）傳。

**Token usage** — 與 Fan event page／Fan product page／Fan bundle page 同一批前台 token（定義在 `fan-shop.css` 最前面的 `.fep-shop { … }`），第 6 段新增的類別沿用同一批、無新 token。

**Consumers** — `create-project.html`（最後一步「預覽與發布」驗證通過後的全頁畫面，D322，`previewRender` 呼叫 `buildFanModel()`）；`publish-work.html`（作品上架最後一步「預覽與送審」，D323，`previewRender` 呼叫同名 `buildFanModel()`，傳 `model.work`／`model.credits`／`model.clips`）；`design-system.html` §4.215（專案頁） 就地渲染 demo（替身 api，直接發行與共創各一份；demo 未涵蓋 D323 的 `work`／`credits`／`clips` 三欄）。
