專案概覽

團隊成員在這頁了解 ztor Creator Studio 的整體架構與共同規格。ztor Creator Studio 是創作者的商業營運後台，讓創作者在同一個地方看清楚作品、粉絲、活動、商品、IP、合作分潤與收入。

產品定位與使用者

每個頁面都要同時服務五個設計目標，並照顧四類主要使用者。各目標的意思，見五個設計目標；四類使用者各做什麼、從哪裡進入，見主要使用者。

五個設計目標

設計目標是每個頁面都要達到的共同標準。

目標意思
透明收入、費率、扣項、資料來源、同步狀態、分潤比例與驗證狀態都清楚可查
降低門檻財務、分潤、IP 授權、活動籌備與外部整合，用白話、範例、預設值與檢核協助理解
任務導向每個主要頁面讓創作者知道此刻能完成什麼
連動一致同一筆收入、粉絲、項目、商品、活動、IP 出現在不同頁面時，用同一個資料來源與同一套狀態語言
合規保守涉及粉絲支持、收益分潤、投資暗示、稅務、付款與跨境收入時，文案保守、可被查核

主要使用者

主要使用者有四類，各自從不同頁面進入後台。

使用者在後台做什麼主要進入頁面
獨立音樂人發布作品、建立預購、賣周邊、辦活動、經營高價值粉絲、看收入總覽、項目、電子商店、活動、粉絲、收入管理
電影產業創作者建立內容項目、管理 IP、招募支持者、登記合作者權益、追蹤項目淨利項目、IP、收入管理
視覺藝術家／插畫師管理商品、授權 IP、追蹤銷售與粉絲消費紀錄電子商店、IP、粉絲、收入管理
IP 擁有者上架或管理成熟 IP、追蹤授權與版稅收入IP、收入管理

粉絲不操作後台，但後台設定的項目、方案、商品、票種、福利與分級，都要能清楚轉譯到粉絲端。

依據：主規格 §1、§2。

權限層與角色

產品分三層：登入頁、平台營運（Admin）、創作者工作區。Admin 怎麼進入創作者工作區代為操作，見Admin 代管；只有 Admin 能按的操作，見Admin 專屬操作；工作區裡有哪些角色，見創作者工作區裡的角色；怎麼進入產品，見登入；權限不夠時畫面怎麼說明，見權限不足時的顯示。

  • Admin 與創作者工作區是兩個不同的權限範圍，不是同一個工作區裡的角色高低

平台營運（Admin）

  • 平台內部營運團隊，範圍跨所有創作者
  • 登入後落地 Creator 管理
  • 不必先選創作者，就能使用 Admin 的各個頁面

創作者工作區

  • 單一創作者範圍內的完整後台
  • 創作者本人登入後落地總覽
  • Admin 在 Creator 管理選定一位創作者後，也能進入這位創作者的工作區代管

Admin 代管

代管是 Admin 在 Creator 管理選定一位創作者後，進入這位創作者的工作區代為操作。

  • Admin 代管時看到的畫面與創作者本人相同
  • 代管時，導覽 logo 前多一個「返回 Creator 管理」入口
  • 代管時，畫面標示「目前操作中的創作者」
  • 代管一律發生在被選定創作者的範圍內，不跨創作者混用資料
  • Admin 還沒選創作者就想進創作者工作區時，畫面說明「請先從 Creator 管理選取一位創作者」並提供入口

Admin 專屬操作

Admin 專屬操作是創作者工作區裡只有 Admin 代管時能執行的操作。

  • 目前有兩個例子：
    • 訂單詳情的「撤銷品項」，前提是營運人員已在平台外完成人工退款
    • 活動詳情的「撤銷票券」，前提同樣是營運人員已在平台外（Stripe）完成退款；bookyay 匯入的活動改在 bookyay 後台撤銷，ztor 的撤銷按鈕停用
  • 創作者本人看得到這類操作，但不能按，畫面說明「需要 Admin 角色」

創作者工作區裡的角色

創作者工作區的操作目前以創作者本人為主。

角色能做什麼
創作者本人所有功能頁的查看、建立、編輯、發布、結算與設定
合作者出現在項目、收益拆解或分潤裡，目前不是能登入後台的完整角色
粉絲不操作後台，只接收後台設定轉譯到粉絲端的內容

登入

所有人從同一個登入頁進入產品，登入後依身分決定起始頁。

  • 登入方式有三種：
    • 電子郵件
    • 手機號碼
    • 第三方帳號（Apple、Google、Facebook、LINE）
  • 登入後的分流只決定起始頁，不改變兩層的架構

權限不足時的顯示

權限不足時，畫面要說明原因，不能只把入口藏起來。

  • 看得到但不能操作時，說明缺少哪種權限、需要什麼角色或找誰
  • 涉及付款、提款、稅務或合作者分潤時，優先保守顯示並要求明確確認

依據：主規格 §3.2.1、§4.1～§4.4、§6.4；D086、D170、D174、D252、D282、D361、D371、D375。

導覽原則

導覽原則決定哪些頁面放在主導覽，哪些從頁內進入。

  • 主導覽只放頂層模組
  • 帶下拉子選單的群組只有 IP、電子商店、粉絲三組，群組本身不是頁面
  • 建立流程、詳情頁與多數子頁都從各自的落地頁進入，不進主導覽
  • 商店設定不在電子商店下拉裡，由電子商店頁的按鈕開啟獨立頁面
  • 從商店設定返回時，還原清單的篩選、搜尋與分頁
  • 編輯活動不是獨立頁面，是活動詳情頁的編輯模式
  • 點草稿項目一律回到建立項目流程續填，不進項目詳情
  • 導覽有頂列與側邊欄兩種模式，預設側邊欄
  • 兩種導覽模式是同一套產品地圖，切換不改變頁面內容

依據：主規格 §3.1、§3.2（頁面與上下層關係以 §3.2.1 產品地圖為準）、§5.1；D110、D169、D181、D184、D193、D281、D347、D372。

主要流程與跨模組連動

創作者的工作常跨好幾個模組，同一份資料在各模組之間以引用相連。創作者怎麼從一個模組走到下一個，見四條主要流程；哪些東西能被其他模組引用、修改時怎麼處理，見可被引用的單元。

四條主要流程

四條主要流程說明創作者怎麼從一個模組走到下一個模組。

流程路徑內容
待辦處理總覽 → 各模組今日待處理導向電子商店的低庫存、活動檢核、IP 到期提醒等
租用 IP 或建立項目IP 市場 → IP 詳情 → 租用或建立項目評估授權條件後租用、詢問，或連到建立項目流程
項目收益項目 → 項目淨利 → 收入管理建立項目時設定預期收益結構
收入發生後，收入管理呈現實際拆解與差異
銷售回寫粉絲電子商店、活動 → 收入管理 → 粉絲商品與票務收入寫進收入管理
購買、報名與互動同時影響粉絲紀錄、分級與福利

可被引用的單元

商品、IP、活動可以被其他模組引用或組合，不只存在於單一頁面。

  • 商品可被項目的方案引用，也可組成組合包
  • IP 可被項目引用，在項目裡只有「IP 租借」這一種身分
  • IP 可在 IP 市場被租用
  • 活動可在總覽、收入管理等處被引用呈現
  • 引用時以來源模組為單一資料來源
  • 被引用的一方修改時，要提示可能影響引用方，例如商品改價時提示已引用該商品的項目方案
  • 收入事件綁定所屬項目，項目綁定使用的 IP 版本
  • 被引用方事後修改，不改寫既有事件的綁定

依據：主規格 §3.1.4、§3.3、§7.6、§7.13；D232。

全域能力

全域能力不是獨立頁面，是各頁面共同調用的能力。每一頁都有的導覽與入口，見全域導覽框架；待辦與狀態提醒，見通知中心；一個項目賺多少，見項目淨利；建立與編輯流程共用的做法，見建立流程的共同行為。

全域導覽框架

全域導覽框架是每一頁都有的導覽與全域操作入口，讓創作者跨頁時維持一致的操作方式。內容區頂端的位置路徑，見麵包屑。

  • 框架提供主導覽、搜尋、通知中心、顯示模式切換與帳戶選單
  • 帳戶選單含個人檔案、設定、登出與四語系語言切換

麵包屑

  • 除了總覽，所有頁面在內容區頂端顯示麵包屑
  • 麵包屑路徑是產品地圖中從頂層模組到目前頁面的上層頁
  • 上層頁可點，目前頁不可點
  • 麵包屑不因進入路徑不同而改變
  • 建立流程自己提供位置與進度，不另加麵包屑

通知中心

通知中心集中呈現需要創作者注意的狀態與待辦。

  • 待辦（需要你處理）在上，通知（狀態更新）在下
  • 每則有來源圖示、標題、一行摘要、時間與來源模組標籤
  • 入口圖示上標未讀數
  • 通知只提醒狀態，點擊一律導向對應功能頁處理
  • 待辦在對應動作完成後自動解除
  • 通知裡的金額一律引用收入管理的口徑，不自行重算

項目淨利

項目淨利回答「這個項目到底賺多少」。

  • 項目淨利出現在建立項目（預期收益結構）、項目詳情（收益摘要）與收入管理（實際拆解）
  • 依財務階梯呈現：總收入 → 直接成本 → 毛利 → 平台費、支付費、稅費與合作者分潤 → 淨利
  • 附上預期與實際的差異
  • 每筆資料附上來源與驗證狀態
  • 自動計算、手動輸入、系統預估與文件驗證分開標示
  • 手動輸入的外部成本不能顯示成平台已驗證

商品主分類與次分類

商品是平台的基礎單位，電子商店、活動、項目共用同一套分類語言。

  • 主分類有三個：實體商品、數位商品、體驗與活動
  • 跨頁引用以最細一層的次分類為準
  • 數位的影視類與音樂類只能透過項目發售，不進電子商店
  • 商品可被項目引用為回饋品
  • IP 資產不能放進項目

詳見商品分類與模組應用。

狀態語言

狀態語言讓同一類資料在不同頁面用同一組狀態詞。

  • 狀態第一次出現要讓人看懂實際含義，例如「待結算」不等於可提領
  • 平台不提供退款，唯一的取消途徑是 Admin 撤銷，撤銷不碰金流
  • 訂單沒有「已退款」狀態
  • 撤銷只改狀態，同時回補庫存、讓領取碼失效
  • 作品審核狀態描述一件送審作品，項目狀態描述整個項目，兩套不能互相代用

財務術語與資料來源

財務術語統一各頁怎麼稱呼與計算收入、扣項和淨利。共創項目的募得款撥付與淨利池分配，見共創項目的兩筆錢。

  • 財務階梯：總收入 − 直接成本 ＝ 毛利，毛利 − 平台費、支付費、稅費 − 分潤 ＝ 淨利
  • 平台費與支付手續費一律由創作者負擔、從收入內扣，買家只付折後售價加運費
  • 手動補登的收入未驗證前，不計入可提領
  • 總覽、項目等頁面不自行重算收入，一律引用收入管理的口徑

折抵與費用負擔詳見優惠規則。

共創項目的兩筆錢

共創項目的募得款撥付與淨利池分配是兩筆錢，規則分開。

  • 募得款由平台分期撥給創作者，期數由平台依項目預算決定，創作者不能選
  • 第 1 期在完成所有扣款後撥付，不需審核
  • 之後各期由 Admin 審核，確認後 14 天內撥付
  • 撥付金額已扣除系統費用
  • 淨利池分給創作者與 NFT 持有者，由創作者手動觸發，不會自動分配

語言與在地化

語言規則決定介面與內容用哪種語言呈現。

  • 產品支援英文、繁中、簡中、印尼語，只有一個「預設語言」，同時決定介面語言與內容的輸入語言
  • 表單只用預設語言輸入，其他語系自動翻譯，原文一改就重新生成
  • 活動例外，其他語系改為手動翻譯
  • 設定頁、帳戶選單、登入畫面改的是同一個預設語言
  • 登入畫面選的語言先只用在登入畫面
  • 登入後與帳號的預設語言比對，不同時詢問要改還是保留
  • 多步驟流程的最後一步是全頁的預覽畫面，主區是粉絲看到的完整頁面
  • 預覽畫面的側欄有語言、幣別與發布前檢核三段
  • 側欄主鈕按下即發布，不再彈第二層確認
  • 發布後，可在活動詳情、商品細節頁、組合商品細節頁重開同一個畫面（預覽與在地化）修改

詳見步驟 7 預覽與發布。

粉絲分級與指標術語

粉絲分級把粉絲依貢獻與關係深淺分成四級。

  • 分級由高到低是核心圈（Inner Circle）> 超級粉絲（Super Fans）> 上榜粉絲（Ranked Fans）> 一般粉絲（Fan）
  • 忠誠點數是排名用的分數，不能花用、不能兌換
  • 升級要同時通過「前 % 名」與「最低忠誠點數」兩道門檻
  • 點數與分級每週重算

詳見粉絲分級。

收入事件與費率版本

收入事件是每一筆進帳的單一、可追溯紀錄，費率版本記下售出當時用的費率。

  • 每一筆收入由來源模組記成收入事件，交收入管理統一彙整
  • 收入事件不可改寫，調整以新的事件表示
  • 售出當下凍結當時的費率版本，平台日後調整費率只影響之後的交易
  • 平台費率分四個收費維度（電子商店、活動、項目、IP），每個維度再分交易子類
  • 某位創作者有平台費率的覆寫值就用覆寫值，否則用全平台預設

計費基準詳見優惠規則。

IP 授權與版本

IP 授權與版本規定授權怎麼生效，以及 IP 的權利狀態怎麼留紀錄。

  • 授權從草稿轉生效，要雙方明確核准且九項條款齊全
  • 授權生效後要改條款，必須開新版本，不原地修改
  • 每個 IP 的版本只增不改，可還原任一時點的權利狀態
  • 收入事件綁定當時的 IP 版本

用詞規則

用詞規則防止可編輯的文字暗示保證報酬。

  • 粉絲權益、群發訊息、公告、共創說明等可編輯文字，不能用 investment、yield、guaranteed payout、ROI、passive income、dividend
  • 可改用 performance-based distribution 這類中性說法

詳見粉絲分級的各級福利。

受眾指標術語

受眾指標術語規定受眾數字用什麼單位、怎麼呈現。

  • 受眾數字分「次數」與「人數」兩種單位，不能互相加總或比較，每個數字都標單位
  • 只存在於會員資料的屬性只能用人數，並揭露涵蓋率
  • 不把多個維度合成單一影響力分數

展示素材

展示素材是各模組用來展示的圖片與影片。

  • 展示素材槽同時收圖片與影片，共用張數額度
  • 全站唯一標準比例是直式 2:3（750×1125px）
  • 展示素材的影片支援 MP4、MOV、WEBM
  • 展示素材的影片單檔上限 1.8GB
  • 展示素材影片的縮圖自動取第一幀
  • 活動另有必填的橫式橫幅（16:9），其他模組不比照

活動素材與專用影片槽詳見步驟 2 基本資料。

年齡分級

年齡分級標示內容適合的觀看年齡。

  • 年齡分級六級單選，預設「全部」：全部、7+、10+、13+、16+、18+
  • 作品上架、建立項目、項目公開資訊三處共用同一份資料

打包單位：組合與方案

組合包與方案都是把多樣東西打包販售的單位。

  • 電子商店的組合包與項目的方案是同一種模式：成員引用既有商品、價格自動推導、折扣用百分比
  • 方案依附於項目，賣的是承諾
  • 組合包獨立存在，賣的是現貨

詳見組合包與票務商品。

項目的組成：作品與方案

項目由「作品」與「方案」構成。

  • 直接發佈、共創、預購三型都有作品
  • 只有共創與預購有方案

詳見商品分類與模組應用。

庫存池、三開關與鎖定庫存

庫存池與三開關決定一件商品在每個販售管道能不能賣、能賣多少。

  • 單售與每個組合包各是一個販售管道，各自有上架、顯示、開賣三個獨立開關
  • 庫存預設共用，任一販售管道可鎖定一部分只給自己賣
  • 有成交只能封存，零成交且已下架或已封存才可刪除

詳見電子商店販售流程、組合包與票務商品、活動規則。

定價幣別

定價幣別決定商品與票券以哪種幣別定價，以及其他幣別怎麼換算。

  • 一位創作者只有一個創作者幣別，由 Admin 建立帳號時從 USD、TWD、HKD、SGD、JPY 選定，之後創作者與 Admin 目前都不能改
  • 每個可販售項目以建立當下的創作者幣別為基準幣別，其他四種幣別自動換算
  • 電子商店的換算價唯讀，活動票價可以逐幣別覆寫
  • 基準價一改，逐幣別的覆寫全部重算
  • 改價只影響之後的購買，已售出不追溯
  • 平台基準幣別是平台自己的記帳幣別，預設港幣；忠誠點數的購買類計分，先把金額換成平台基準幣別再算分，見粉絲分級

詳見步驟 7 預覽與發布、組合包與票務商品。

商品屬性與選項標準值

商品屬性與選項標準值讓商品資料能跨商品統計。

  • 商品資料分四種：分類、系統屬性、選項、自訂規格
  • 需要拿來統計或篩選的做成固定欄位，只給買家看的說明放自訂規格
  • 尺寸與顏色有平台標準值

詳見商品屬性、尺寸與顏色的快捷預設與自行輸入。

需求估算

需求估算依市場統計商品的尺寸分布，並給出簡單的需求量預測，讓創作者在下生產單之前知道各尺寸要做多少。

  • 只供參考，不連動庫存、出貨規則或生產單
  • 需求看板與單一商品的數據用同一套算法

詳見需求看板。
