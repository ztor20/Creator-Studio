# 規則手冊撰寫規則

適用：新增或修改 `app/rulebook/` 的任何頁面。

本檔只管「怎麼寫」。另外兩件事在別處定義：

- 內容從哪來、何時同步：專案根 `CLAUDE.md`「規格定案後同步規則手冊」
- 樣式、章節樹、版本參數：`site/CLAUDE.md`「規則手冊」

## 維護本檔

- 使用者對手冊寫法、結構或樣式提出新要求或修正時，同一輪就把它寫進本檔，再去改頁面；不只改頁面
- 新規則若跟本檔既有條文衝突，改寫舊條文，不並存兩種說法
- 改完本檔，回報時說明加了或改了哪一條

## 讀者

- ztor 團隊所有人，包含完全不懂工程的人
- 寫完自問：沒看過規格的設計師或 PM，讀一次能不能懂

## 五條核心原則

1. 用最少的字：能用一句就不寫一段，能用表格就不寫段落
2. 基本規則優先：先寫規則本身，再寫例外；推導出來的延伸情境能省就省
3. 指涉要清楚：不用「它」「這個」「那邊」「上述」指代不明的東西，每句直接寫出主詞
4. 不用工程術語：必要的專有名詞第一次出現時，用括號白話解釋
5. 標題要自己說得清楚：頁面與小節標題要讓沒看過規格的人一看就知道內容，不用「分級與分工」這種把兩件事縮成一個詞的標題

## 頁面骨架

依序排列：

1. 標題：子頁名稱
2. 導言：最多兩句。第一句固定用「誰可以用這頁做什麼」的句型，例如「創作者把圖片、影片、音檔放進庫房，只開放給符合條件或拿到鑰匙的粉絲」
3. 流程圖：功能的流程牽涉兩方以上或要好幾步才走完時才放，見「呈現形式」的流程圖條
4. 目錄：大節（`<h2>`）加子節（`<h3>`）的總數有 3 個以上就放，不到 3 個不放；只寫一個空的 `<div class="toc"></div>`，由 `shell.js` 自動列出各 `<h2>` 與其下的 `<h3>`（`<h3>` 縮排在所屬 `<h2>` 底下，`<h4>` 不列），每項帶自動序號、可點擊跳轉；作者不手寫連結與序號
5. 各節：先規則節、後畫面節，見「一頁的節分兩類：先規則、後畫面」
6. 頁尾，預設收合，依序放：
   - 來源：規格檔、版本、D 編號
   - 尚待確認清單
   - 最近同步日期

### 不放進頁面的資訊

- 討論過程與決策沿革，例如「原本是…後來改成…」
- 頁首的長串規格檔與 D 編號（改放頁尾來源）
- 其他頁的規則（寫一句話並連過去）
- 跨頁導覽與其他功能的介紹：子頁只寫該功能頁本身，不介紹同一章的其他頁，也不提還在草稿或未定案的頁面
- 原型的畫面細節，例如按鈕顏色、版面位置，除非該細節本身就是規則

## 每一節的寫法

### 一頁的節分兩類：先規則、後畫面

- 規則節：跨頁通用的概念，例如活動的階段、販售時間，其他頁也會連過來引用
- 畫面節：這一頁畫面上的功能，例如活動清單
- 一頁有兩類內容時，規則節排前面、畫面節排後面，各自是一個 `<h2>`
- 一頁可以有多個規則大節或多個畫面大節；同類大節相鄰排列，仍是全部規則大節在前、畫面大節在後
- 概念集中在規則節講，不和畫面功能並列成同級的節；畫面節要用到某個概念時，寫一句話並連到規則節
- 畫面節裡照「照功能分小標題」切小節

### 有生命週期的主題，規則節照固定順序分子節

- 主題有生命週期（例如活動、組合包）時，規則節底下的 `<h3>` 子節依序排：

| 順序 | 子節 | 回答什麼問題 |
|---|---|---|
| 1 | 階段 | 走到哪一步、各階段誰能做什麼；放「階段 × 角色」表 |
| 2 | 時間 | 什麼時候看得到、什麼時候買得到 |
| 3 | 動作 | 能做哪些動作（例如取消、撤銷、刪除、上下架、暫停），各自的條件與效果 |
| 4 | 連動 | 主題變動時，相關的對象（例如票務商品）怎麼跟著變 |
| 5 | 來源差異 | 只有某一類對象才有的例外，例如 ztor 自建與 bookyay 匯入的差別 |

- 沒有的子節就略過，其餘順序不變
- 規則獨立成一頁時（例如活動規則 `event-rules.html`），這些子節直接升成該頁的 `<h2>` 大節，照同樣順序排，讓序號短一層
- 子節裡的細項用 `<h4>` 分組
- 同一條規則只寫在一個子節；其他子節要提到時，寫一句話並連過去
- 子節標題照「標題要自己說得清楚」寫成完整的名詞短語，例如「活動的階段」，不只寫「階段」兩個字

### 照功能分小標題

- 適用畫面節；規則節的子節照上一條的固定順序
- 小標題寫「功能名稱」，例如「排行榜」「名人堂」，不寫畫面位置（例如「頁首」「側欄」）
- 小標題底下第一句寫這個功能是什麼、滿足創作者什麼需求，依據規格每個功能的「目的」，不自己發揮；不加「用途」之類的標籤
- 接著才寫規則：表格或條列
- 只服務某個主要功能的附屬功能（例如清單的搜尋、篩選、匯出），收進那個主要功能底下，用 `<h4>` 當更小一層的標題，不另立小節；判斷依據是原型畫面上它跟著哪一塊
- 子節標題不重述上一層的名稱：`<h2>`「活動清單」底下的 `<h3>` 寫「清單」「統計」「沒有資料時」，不寫「活動清單」「活動統計」
- 規則節的子節不受上一條限制，照「有生命週期的主題」那條寫成完整名詞短語（例如「活動的階段」），因為其他頁會單獨連過來引用

### 序號

- 序號由 `shell.js` 依章節樹自動產生，格式是「章.頁.節.小節」，例如 `7.1.2.3`
- 子功能頁只是分組，不編號；待補的頁也佔號，補上內容時其他頁不會跳號
- `<h1>`、`<h2>`、`<h3>` 用數字序號；`<h4>` 自動加字母 a、b、c，每個 `<h3>` 重新起算（`<h4>` 直接在 `<h2>` 底下時以該 `<h2>` 重新起算），作者不手寫；卡片裡的標題不加
- h2 與 h3 的開頭段落要帶到底下的子節：用一句話說明各子節回答什麼，並連到該子節（例如「見活動的階段」「見各階段誰能做什麼」）；連到 h2、h3、h4 的頁內連結會自動帶上同一個序號或字母，作者只寫標題文字；這類頁內章節參照會自動顯示成行內小標籤，與前後文字分開
- 子節超過 6 個時，開頭段落不硬寫成一長句：改成照子節順序條列子節名稱連結，或把連結放進已有的表格（例如步驟表的步驟欄）
- 大節或子節底下只有 1 個子節時，開頭段落不用連過去
- 開頭段落已用連結帶到底下的 h4 時，不再自動產生子節目錄；新寫或改寫的頁一律用開頭段落帶出 h4，自動子節目錄只是還沒改寫的頁的後備
- 一個 `<h3>` 底下有 3 個以上 `<h4>` 時，`shell.js` 會在該 `<h3>` 標題下方自動產生一排子節目錄（各 `<h4>` 的跳轉連結，帶字母），作者不用手寫；`<h4>` 沒寫 id 也會自動補上（開頭段落已用連結帶到這些 h4 時略過，見上一條）
- 頁面裡不手寫序號與字母；`<h2>` 保留 `<span class="n"></span>` 讓程式填入即可

### 句子與依據

- 標題用名詞短語，直接說這節管什麼，例如「什麼算可賣」
- 第一句寫結論，接著用條列或表格展開
- 每條規則一句話，只寫「什麼情況下會怎樣」，不寫背景與理由
- 刪字時保留必要的原因短語，例如寫「不能，由品牌條件決定」，不只寫「不能」
- 例子裡的數字要寫明是假設，例如「假設門檻設 800 點」，避免被當成真實規定
- 規格寫「本期」「目前」的限制，照樣保留這兩個字
- 結尾一行「依據」，用小字寫規格檔、F 編號或節號、D 編號
- F 編號與 D 編號只出現在「依據」行與頁尾來源，不進正文

### 標題與項目名稱寫「管什麼」，不寫「怎麼算」

- 節標題回答讀者想問的事，例如「粉絲怎麼升級」；不直接搬規格的設定欄位名或內部機制名當標題
- 倍率、權重、係數、參數、上限這類字描述的是計算方式，只放在說明句或公式裡，不當標題，也不當表格項目的名稱
- 表格項目的名稱寫它調整的對象：寫「購買、活動報到、互動、推薦的計分比重」，不寫「行為倍率」；要對照畫面時，把畫面用詞放括號，例如「（畫面上的『行為倍率』）」
- 一節在講一個流程（例如升級、退款），開頭先用步驟把整個流程走完一次，再展開各步驟的細節

### 狀態型主題用「階段 × 角色」表切入

- 主題有生命週期（例如活動、組合包、項目）時，在規則節的「階段」子節先用一張階段 × 角色表交代每個階段下誰能做什麼
- 每一列一個階段；欄位依序是什麼時候進入、創作者能做、Admin 額外能做、連動（例如票務商品、持票人）
- 「Admin 額外能做」只寫創作者做不到的事
- 格子只寫主線規則，每格最多約 3–4 條
- 只有某一類對象才有的例外（例如 bookyay 匯入的活動）不塞進每一格，另做一張對照表，放在規則節的「來源差異」子節，例如「ztor 自建與 bookyay 匯入的差別」：每一列一件事，欄位是兩種來源各自的規則
- 放不進格子的事（例如階段怎麼判定）寫成表格下方的短註；屬於動作、連動或來源差異的，放進對應的子節，不留在表格下方
- 短註超過約 5 條，或混了不同主題時，依主題用 `<h4>` 小標題分組，各組自己列；不寫成一長串
- 流程標籤（A → B → C）保留，放在表格上方一行交代階段順序

## 呈現形式

選最省字的那一種：

| 內容 | 用什麼呈現 |
|---|---|
| 狀態、欄位、前後對照 | 表格 |
| 有先後順序的流程 | 步驟 |
| 兩到三個並列的概念 | 卡片 |
| 生命週期、狀態怎麼轉換 | 流程標籤（A → B → C） |
| 各階段下誰能做什麼 | 階段 × 角色表，見「狀態型主題用『階段 × 角色』表切入」 |
| 有公式或數字的規則 | 互動試算 |
| 一個例子就能講清楚的規則 | 範例框 |
| 牽涉兩方以上或好幾步才走完的整條流程（例如創作者設定、粉絲達成、結果回到創作者） | 流程圖，見下方流程圖條 |
| 好幾段時間誰包住誰、誰早誰晚（例如上架、開賣、門票販售） | 時間軸圖，見下方時間軸圖條 |

- 條列一項只講一件事，不用頓號或分號串起好幾件事
- 單項超過兩行，考慮拆開或改成表格

### 流程圖

- 什麼時候放：功能的規則牽涉兩方以上（例如創作者與粉絲、創作者與 Admin），或要好幾步才走完一次（例如設定 → 粉絲達成 → 解開），就在導言下方放一張流程圖
- 什麼時候不放：只有單一設定、沒有先後順序的功能
- 畫什麼：把整條流程從頭走到尾一次，每一步寫誰做、做什麼
- 分岔寫成問句（例如「符合條件嗎？」），出口寫結果
- 只畫已定案的規則：還沒定的步驟不畫，或標「尚待確認」並在頁尾列出
- 畫法比照活動用戶旅程圖（`event-journey.html`）：用頁面本身的 HTML 與樣式畫，不引用外部繪圖程式庫
- 窄螢幕要能橫向捲動
- 流程很長、要獨立成頁時（例如活動），本頁導言放一句連到流程圖頁即可
- 流程圖不取代正文：圖只交代順序與分岔，規則細節仍寫在各節

### 時間軸圖

範本是活動規則「活動的販售時間」（`event-rules.html#timing`）。

- 什麼時候放：規則在講好幾段時間的包含與先後，例如哪一段要落在哪一段裡、可不可以早於另一段
- 一列一條時間線，時間由左到右
- 列名的格式跟同一節表格的第一欄一模一樣：同色標籤寫「管什麼」的名稱（例如上架、活動開賣），底下灰字寫規格用詞（例如上架區間 · Listing period）；不寫「第一層、第二層」這類序位
- 色條裡寫這一段是什麼（例如上架期間、早鳥、照活動開賣）；放得下就寫，放不下就不寫，不硬塞
- 同一條時間線分成兩段時（例如早鳥接正式販售），兩段之間用細虛線隔開，對齊造成分段的那個時間點
- 每個關鍵時間點畫一條貫穿各列的虛線，底部時間軸寫時間點名稱（已經寫在色條分段裡的時間點，例如早鳥、預售的起點，底部可以不再寫）；主要時間點用粗體，可選的時間點用一般字重；名稱擠在一起時錯開成兩行
- 色條畫成規則的預設值，例如門票販售預設跟活動開賣同一段，早鳥只是讓它提早開始
- 有生命週期的主題，最上面加一列階段（例如已排程、售票中、進行中、已結束），標出每個階段落在時間軸的哪一段
- 看得到但還不能買這類過渡期（例如預告），畫成淡色虛線框的一段
- 隨時可能發生、跟時間點無關的狀態（例如暫停售票、完售、取消、手動下架）不畫進圖；圖下說明寫一句「不畫在圖上」並連到寫這些規則的段落
- 圖下說明用一段話講圖要怎麼讀，以及圖表達了哪幾條規則
- 窄螢幕時列名移到色條上方，貫穿各列的虛線不顯示

## 用詞

- 用產品畫面上的實際用詞；介面是英文時，中文後面括號附英文
- 同一個概念全手冊只用一個詞，例如「販售管道」「售票期間」；拿不準就查主規格 §7 共用規格
- 引用其他頁寫頁名並加連結，不寫「第 N 章」「第 N 節」
- 數字、金額、期限照規格原值寫，並附單位

### 角色只有創作者與 Admin，系統不是角色

- 角色只寫創作者與 Admin，不另立「系統」角色，也不拿「系統」當句子主詞
- 自動發生的事寫在觸發它的那一格，寫成那個動作或時間點的後果：
  - 由某個角色的操作觸發的，寫在那個角色那一格，例如「取消後，持票人會收到取消通知」
  - 由時間觸發的，寫在那個階段，例如「活動結束時，上架中的組合包自動下架」
  - 由外部平台（例如 bookyay）觸發的，寫明來源，寫成短註，不寫成某個角色做的
- 純計算的結果寫「自動算出」「自動加總」，不寫「系統算」
- Admin 能做創作者能做的一切（代管）；寫 Admin 時只寫額外能做的：創作者介面上只有 Admin 能按的操作，以及 Admin 專屬介面能做的事

## 尚待確認

- 正文不寫還沒定案的內容
- 頁尾的「尚待確認」清單一條一句，寫清楚「什麼還沒定」

## 子頁怎麼切

- 一個子頁對應一份規格分頁，或原型的一個頁面
- 超過約 8 節就拆成兩頁
- 一章的子頁同樣先規則、後畫面：跨頁通用的規則與整體說明（例如活動規則、活動用戶旅程圖、bookyay 匯入與對照）放在章首的「規則」分組，各畫面的子頁（例如活動總覽、建立活動、活動詳情與編輯）放在後面的分組；分組在 `shell.js` 的 `TREE` 設定，分組本身不編號
- 某一頁的規則節被好幾頁共用時，把它獨立成規則頁放進規則分組，原頁只留畫面；搬走的錨點在原頁加轉址，舊連結不斷
- 外部系統的匯入與欄位對照（例如 bookyay）屬跨頁通用的規則，放在規則分組；該系統在 Admin 端的管理畫面仍放在 Admin 章

## 完成前檢查

1. 刪字：每句再問一次「拿掉這句，讀者會看不懂嗎」，不會就刪
2. 驗收：請一位沒參與撰寫的檢查者（人或 AI）對照規格逐條核對，確認三件事：
   - 事實正確
   - 沒把待確認寫成定案
   - 每節都有「依據」
3. 名稱掃描：把所有標題與表格第一欄掃一遍，出現倍率、權重、係數、參數這類計算用語，或直接搬自規格的欄位名，就改寫成「管什麼」的名稱
4. 角色掃描：全頁搜尋「系統」，當主詞或當角色用的，照「角色只有創作者與 Admin，系統不是角色」改寫
5. 階段 × 角色表掃描：格子裡不出現只屬某一類對象的例外（改放對照表），每格不超過約 4 條；表後短註超過約 5 條或混了不同主題的，已用 `<h4>` 依主題分組
6. 節的分類掃描：規則節在前、畫面節在後，同類大節相鄰；概念沒有和畫面功能並列成同級的節；有生命週期的主題，規則節子節照「階段 → 時間 → 動作 → 連動 → 來源差異」排，同一條規則沒有寫在兩個子節
7. 章節說明掃描：每個 h2、h3 的開頭段落都用連結帶到底下的子節（只有 1 個子節時免；超過 6 個時改用條列或表格裡的連結，不寫成一長句）；章節參照只寫標題文字，序號、字母與小標籤樣式自動產生
8. 目錄掃描：大節加子節總數 3 個以上的頁有 `<div class="toc"></div>`，不到 3 個的頁沒有
9. 章的分組掃描：跨頁通用的規則與整體說明在章首的規則分組，畫面子頁在後；沒有規則節被好幾頁重複寫
