DEMO 票務商品（建立活動第 6 步）重新設計提案。假資料＝三場的粉絲見面會，每場兩種票。

票務商品

把門票和商品綁成一組賣。沒有要綁就直接下一步。

捆綁包

一組至少含一張票。數量跟它含的那張票共用，賣掉一組就從那張票扣一張，不另外設庫存。

這一步的影響

為什麼這樣排

順序倒過來：內容 → 定價 → 包裝

現行版本的欄位順序是名稱＊ → 說明 → 封面圖 → 適用票種 → 商店商品 → 販售上限 → 額外權益 → 套組優惠，等於要創作者先替一個還沒有內容的盒子取名字、上傳封面。腦中的句子其實是「VIP 票 ＋ 巡演 T 恤，賣 4,800」——先有內容，才有名字與價格。名稱移到最後之後，可以直接從內容自動擬一個建議名，必填欄從空白格變成確認一下就好。

適用票種：分組、捷徑、選完就收

三場兩種票時，現行的平面勾選清單就佔 419px；十場的活動會長到約 1,900px，一個欄位吃掉兩個畫面。這裡改成依場次分組（組頭可整場全選）、加一排跨場次的票種捷徑，並在選完之後收合成 chip，清單只在挑選當下展開。卡片高度因此不再隨場次數膨脹。

空狀態要能說「不綁」

副標寫著「沒有要綁就直接下一步」，但畫面上只有一顆「＋ 新增捆綁包」，沒有任何「不綁」的動作。多數活動不會做捆綁包，這是這一步最常見的結果，該有正式出口——同時用一個具體例子把「數量池共用」講清楚，那是站上的新概念。

右軌報影響，不報清單

原本的「票的數量池」把左邊勾選清單的同一份票再列一次。改成用到的票排前面並標「被 N 組用到」，沒被綁到的收成一行——右軌要回答的是「我改這張票的張數會牽動誰」。

這份 demo 替三個待裁決的問題各給了一個答案

  • 多選票種在多場活動下是什麼意思 — demo 保留現行語意（勾起來的票都適用，粉絲買的時候挑一種），並在算式旁明講「賣掉一組，就從粉絲挑的那一張扣一張」。若正式版要改成「一組只對應一張票」，捷徑那一排就不需要了。
  • 要不要每場各建一組 — demo 在適用票種上方放了「一組通用所有場次／每場各一組」二選一。選後者時只挑票種，按下建立會一次長出三組（Day 1／Day 2／Day 3），省掉手動複製三次。
  • 命名要不要移到最後 — demo 移到最後，並附自動建議名。收合列的辨識靠名稱，所以中途離開仍會留下「未命名套組」；建議名讓這個風險降到最低，但沒有完全消除。

順帶會修掉的兩件事

  • 卡頭摘要現在寫「1 份作品」——那是募資版的字彙漏過來的（判斷條件掛在「有沒有分潤名額」而不是「有沒有作品」）。活動的捆綁包裡是票和商品，摘要應該報「1 張票 · 2 件商品」。
  • create-event.html 的右軌用的是 .wizard-split__side，但元件裡只有 .wizard-split__rail。靠 grid 自動配位剛好落在對的格子，所以看起來正常，實際上 sticky、最大高度與疊卡間距全部沒生效。本 demo 用的是正確的 __rail。
